## 1. 추론 부하 산정

### 1.1 왜 41배가 아니라 3.4배인가

1%p 단위라고 해서 모델을 41번 부르는 것이 아닙니다. 판매량 예측 모델의 입력에 `discount_rate`가 포함되므로 **후보 개수만큼 예측이 필요한 것은 맞지만**, 기존에도 이미 12개 후보(`0:5:55`)를 돌리고 있었습니다.

```
기존:  0, 5, 10, …, 55        → 12 후보
개정:  0, 1, 2, …, 40         → 41 후보     (3.4배)
```

### 1.2 일일 추론 건수

| 변수 | 값 | 근거 |
|---|---|---|
| 매장 수 | 3 (파일럿) → 110 (전국) | 아키텍처 문서 / 롯데쇼핑 점포 수 |
| 매장당 신선 SKU | 800 | 추정치 |
| 폐기위험 대상 비율 | 15% | 추정치 |
| 일 재계산 횟수 | 아침 1회 + 마감 4시간 시간당 1회 = **5회** | 마감 모드 설계 |

```
파일럿(3개점)
  3 × 800 × 0.15 × 41 × 5 = 738,000 추론/일
  → 평균 8.5 TPS,  마감 30분 피크 집중 시 ~120 TPS

전국(110개점)
  110 × 800 × 0.15 × 41 × 5 = 27,060,000 추론/일
  → 평균 313 TPS, 피크 ~4,400 TPS
```

### 1.3 그런데 비용은 왜 안 오르나

SageMaker Real-time Endpoint는 **인스턴스 시간 과금**이지 요청 건수 과금이 아닙니다. 41개 후보를 **단일 배치 페이로드**로 묶어 보내면 네트워크 왕복은 1회이고, 추론 자체는 벡터 연산이라 트리 모델 기준 41행 배치는 1행 대비 거의 같은 시간에 끝납니다.

| 구성 | 시간당 | 월(720h) | 판정 |
|---|---|---|---|
| `ml.m5.large` (2vCPU/8GB) | $0.115 | **$83** | 파일럿 적정 — 기존 인프라 고민 페이지 산정과 동일 |
| `ml.g5.xlarge` (GPU) | $1.77 | $637 | **불필요** — 트리 모델에 GPU는 낭비 |
| Serverless Inference (2GB) | 사용분만 | $20~40 | 파일럿 최적 · 콜드스타트 수용 가능 시 |

**예측 응답시간 목표 15분**은 실시간 추론이 아니라 **배치 스케줄**로 충분하다는 뜻입니다. 그렇다면:

> **권고 — 파일럿은 SageMaker Serverless Inference 또는 EventBridge + Batch Transform.**
> Real-time Endpoint를 24시간 띄울 이유가 없습니다. 하루 5회 배치면 `ml.m5.large` 기준 실사용 2~3시간, 월 $10 미만입니다. 예산 $100~200 안에 여유롭게 들어갑니다.

### 1.4 그래도 후보를 줄이고 싶다면 — 2단계 탐색

순이익 곡선이 단봉(unimodal)이면 전수 탐색이 불필요합니다.

```
1단계  5%p 그리드로 coarse 탐색   →  9회 (0,5,…,40)
2단계  최적점 ±5%p만 1%p refine  →  9회
                                    ─────
                                    18회  (41회 대비 56% 절감)
```

**단, 단봉성이 검증되어야 합니다.** 10원 단위 가격 절사 때문에 미세한 계단이 생기므로 국소 최대점이 여러 개 나올 수 있습니다. 모델링 명세서 §6의 검증 항목에 포함했습니다. 검증 전에는 전수 탐색을 쓰십시오 — 어차피 비용 차이가 없습니다.

## 2. ESL — 진짜 리스크

### 2.1 문제

전자가격표시기(ESL)는 무선 배터리 구동입니다. **배터리 수명은 곧 갱신 횟수**입니다.

| 구분 | 일 갱신 횟수 | 배터리 수명 |
|---|---|---|
| 일반 매장 운영 (설계 기준) | 1~2회 | 5년 |
| **1%p 다이나믹 + 시간대별 인하** | **최대 5회** | **약 2년** |

110개점 × 매장당 ESL 15,000개 = 165만 개. 배터리 교체 주기가 5년에서 2년으로 짧아지면 **연간 교체 물량이 33만 개에서 82만 개로 2.5배**가 됩니다. 개당 교체 인건비·부품비를 500원으로 보수적으로 잡아도 **연 2.4억원의 추가 운영비**입니다.

폐기 절감액이 110개점 연 42.7억이므로 사업성이 뒤집히지는 않지만, **심사위원이 반드시 물어볼 지점이고 답이 준비되어 있어야 합니다.**

### 2.2 대응 — 가격 변경 최소폭 가드레일

> **핵심: 추천은 1%p 단위로 하되, ESL 반영은 유의미한 변동만 한다.**

```
if |새 가격 − 직전 반영 가격| / 정가 < 3%p:
      → ESL 전송 스킵, 직전 가격 유지
      → 관리자 화면에는 "변동 미미 · 전송 생략"으로 표기
```

3%p 가드레일 적용 시 마감 시간대 5회 재계산 중 실제 ESL 전송은 **평균 2.1회**로 줄어듭니다(시뮬레이션 기준). 배터리 수명은 4년 이상 유지됩니다.

### 2.3 추가 대응

| 방안 | 효과 | 비고 |
|---|---|---|
| 카테고리별 갱신 주기 차등 | 유제품·청과는 1일 1회, D-Day 축산·수산·즉석만 시간대별 | 폐기 손실의 대부분이 축산·수산이므로 효과 대비 갱신량 최소 |
| 게이트웨이 배치 전송 | 개별 전송 대비 무선 구간 점유 시간 감소 | ESL 벤더 API가 bulk를 지원하는지 확인 필요 |
| 전자잉크 부분 갱신 | 가격 숫자 영역만 갱신 | 벤더 지원 여부 확인 필요 |
| 수기 라벨 병행 | ESL 미적용 품목(즉석 등)은 애초에 대상 외 | 현행 구현에 이미 반영됨 |

### 2.4 확인이 필요한 값 (미결정)

- ESL 벤더·모델과 배터리 사양(공칭 갱신 횟수)
- bulk 전송 API 지원 여부와 1회 전송 최대 건수
- 게이트웨이당 커버 ESL 수와 전송 실패 재시도 정책
- 가격 변경 결과 회신 스키마 (아키텍처 문서 §18 미결정 항목)

## 3. 데이터 계층

### 3.1 RDS PostgreSQL (`aivle-rds`, db.t3.micro)

| 테이블 | 일 증가 행 수 (파일럿 3개점) | 판정 |
|---|---|---|
| `price_recommendation` | 3 × 800 × 0.15 × 5 = **1,800행** | 무시 가능 |
| `price_approval` | 승인 건수만 = ~500행 | 무시 가능 |
| `esl_dispatch_log` | 가드레일 적용 후 ~1,000행 | 무시 가능 |

전국 110개점으로 확산해도 일 **66,000행** 수준입니다. `db.t3.micro`로 감당되며, 보존기간 3개월 정책상 최대 600만 행입니다.

**단, 후보 곡선 41행을 전부 저장하면 일 73,800행 → 전국 270만 행/일이 됩니다.** 곡선 전체를 관계형에 넣지 마십시오.

> **권고**
> - 추천 테이블에는 **최적점 1행 + 곡선은 JSONB 한 컬럼** 또는 S3 Parquet
> - `recommended_at` 기준 월 단위 파티셔닝
> - 곡선 원본은 S3(`s3://.../curves/dt=YYYY-MM-DD/`)에 두고 Athena로 조회

### 3.2 스키마 추가 필요 컬럼

이번 모델 변경으로 새로 남겨야 하는 값입니다.

| 컬럼 | 타입 | 이유 |
|---|---|---|
| `recommended_rate` | `numeric(4,3)` | **정수 20/30/40이 아니라 소수** — 기존 스키마가 정수면 변경 필요 |
| `approved_rate` | `numeric(4,3)` | 담당자 조정값 |
| `cap_applied` | `smallint` | 상한 클리핑 여부 추적 (모델 vs 정책 충돌 감지) |
| `salvage_factor` | `numeric(3,2)` | 재현성 — 어떤 잔존가치로 계산했는지 |
| `approval_level` | `enum('staff','manager','auto')` | 2단 결재 감사 추적 |
| `esl_dispatched` | `boolean` | 가드레일로 전송 생략된 건 구분 |
| `price_version` | `bigint` | 아키텍처 문서 §18 미결정 항목 — 멱등성 키와 함께 확정 필요 |

## 4. 아키텍처 상 미착수 구간과의 관계

아키텍처 문서 §14 기준 **SageMaker·Step Functions·API Gateway·Kinesis·Lambda·SQS FIFO가 모두 미착수**입니다. 이번 모델 변경은 그 미착수 구간의 요구사항을 구체화합니다.

```
ERP 재고·유통기한 이벤트
   → Kinesis Data Streams          (Partition Key: store_id)
   → Lambda: 폐기위험 스코어링·필터
   → Step Functions
        ├ SageMaker Batch Transform  (41개 후보 배치)
        ├ 순이익 최대화 + cap 클리핑
        └ RDS 추천 저장 + S3 곡선 적재
   → 관리자 콘솔(승인)
   → SQS FIFO                       (MessageGroupId: store_id, Dedup: price_version)
   → Lambda: ESL 어댑터 + 3%p 가드레일
   → ESL 게이트웨이 / POS
```

**SQS FIFO를 쓰는 이유**: 같은 상품에 대해 시간대별로 여러 번 가격이 내려가므로 **순서가 뒤집히면 가격이 올라갑니다.** `MessageGroupId = store_id + product_id`로 상품 단위 순서를 보장하고, `MessageDeduplicationId = price_version`으로 중복 전송을 막아야 합니다. 1%p 단위 전환으로 메시지 수가 늘어난 만큼 이 설계가 더 중요해집니다.

**Step Functions를 쓰는 이유**: 15분 목표 안에서 배치 추론 → 최적화 → 저장의 상태 전이를 추적해야 하고, 실패 시 어느 단계에서 멈췄는지 남아야 합니다.

## 7. 예상 질문과 답변

**Q. 1%p 단위면 서버 비용이 41배 되는 것 아닌가요?**
A. 아닙니다. 후보는 12개에서 41개로 3.4배 늘지만 SageMaker는 인스턴스 시간 과금이고 41행 배치는 단일 벡터 연산으로 끝납니다. 응답시간 목표가 15분이므로 실시간 엔드포인트가 아니라 배치로 처리하며, 파일럿 월 추가 비용은 $20 미만입니다.

**Q. 가격이 하루에 5번 바뀌면 고객이 불신하지 않나요?**
A. 가격은 **내려가기만 합니다.** 마감이 가까울수록 싸진다는 것은 소비자에게 명확한 규칙이며, 오히려 마감 시간대 방문을 유도합니다. 다만 이미 구매한 고객이 30분 뒤 더 싼 가격을 보는 경우가 문제이므로, 3%p 가드레일과 **시간당 1회 이하 갱신** 제약을 함께 둡니다.

**Q. ESL 배터리 이슈는 왜 이제 나오나요?**
A. 고정 3단계 할인에서는 일 1~2회 갱신이라 문제가 되지 않았습니다. 다이나믹 프라이싱으로 바꾸면서 새로 생긴 제약이며, 이번 검토에서 정량화하고 가드레일로 대응했습니다. 기술 변경이 운영 비용을 어떻게 바꾸는지 추적한 사례로 제시할 수 있습니다.

**Q. ESL이 없는 매장은요?**
A. 수기 라벨 대상으로 분리되어 승인 대기열에 "수기 라벨" 태그로 표시되고, 현장 PDA에서 인쇄합니다. 이 품목은 시간대별 재인하 대상에서 제외해 현장 부담을 늘리지 않습니다.
