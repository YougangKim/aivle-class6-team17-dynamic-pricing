# 신선

**신선을 선도하다** — 신선식품 폐기저감 · AI 다이나믹 프라이싱 관리자 콘솔

AI가 순이익이 가장 커지는 할인율을 **0~40% 사이에서 1%p 단위로 추천**하고,
담당자가 **승인**하면 ESL에 즉시 반영됩니다. (30% 초과는 점장 최종 승인)
점장이 **반려하면 사유가 제약조건이 되어 AI가 다시 계산**합니다 — 프로세스가 끊기지 않습니다.

## 문제

롯데마트 한 점포가 1년에 버리는 음식물은 **84.5톤**, 손실로 환산하면 **연 3.86억 원**입니다.
현장 인터뷰에서 확인한 원인은 명확했습니다.

> "발주는 담당자 역량입니다." — 롯데마트 양평점 부점장 (2026.07.09)

폐기는 **발주 시점**과 **할인 시점** 두 곳에서 결정되는데, 두 판단 모두 사람의 감에 의존하고 있습니다.

## 해결

AI는 가격을 결정하지 않습니다. **추천만 하고 최종 판단은 사람이 합니다.**

```
재고 · 유통기한 · 수요예측 · 날씨
        ↓
AI 할인율 추천 (0~40% · 1%p 단위 · 순이익 최대화)
        ↓
담당자 승인 ──── 30% 이하 ────────────────→ ESL · POS 즉시 반영
        │
        └─ 30% 초과 → 점장 최종 승인 ─ 승인 ─→ ESL · POS 즉시 반영
                              │
                              └ 반려 → 사유를 제약으로 AI 재추천
                                        → 담당자 재검토 → (임계값 초과 시 점장 재결재)
                                        → 2회 소진 시 수동 지정 / 할인 미적용으로 종결
```

## 핵심 설계

### 1. 다이나믹 프라이싱 — 왜 상품마다 할인율이 다른가

```
수요반응   p(r) = p₀ + (p_max − p₀) / (1 + e^(−k(r − r₅₀)))
목적함수   net(r) = Q·p(r)·(할인가 − 원가)
                 − Q·(1−p(r))·(원가 + 폐기처리비)·(1 − salvage(d))
최적해     r* = argmax net(r),  r ∈ {0,1,…,상한},  동점 시 최소 r
```

카테고리별 **반응 중점**(유제품 12% · 청과 15% · 즉석 18% · 수산 20% · 축산 22%)과
잔여일별 **이월 잔존가치**(D-Day 0 · D-1 0.40 · D-2 0.62)를 함께 계산합니다.
그 결과 같은 날 대기열에서도 추천이 **16% ~ 36%로 흩어집니다.** 고정 단계가 아닙니다.

`r = 0`은 "조치 불필요"라는 AI의 명시적 판단이며, 대기열이 아니라 미추천 사유 목록에 남습니다.

> 상세 수식·파라미터·검증 항목: [`docs/모델링_명세_다이나믹프라이싱.md`](docs/모델링_명세_다이나믹프라이싱.md)

### 2. 왜 상한이 40%인가 — 정책 시뮬레이터로 증명

| 할인 상한 | 폐기 감축 | 110개점 연 순효과 |
| --- | --- | --- |
| 20% | 21.1% | 26.9억 |
| 30% | 31.0% | 39.8억 |
| **40% (현행)** | **33.7%** | **42.7억 — 최적** |
| 50% | 34.2% | 42.7억 |
| 70% | 34.2% | 41.4억 |

40%를 넘으면 소진 개선은 포화되고 마진 손실만 늘어 순효과가 감소합니다.

### 3. 2단 결재

| 할인율 | 결재 |
| --- | --- |
| 1 ~ 30% | 담당자 승인 → ESL 즉시 반영 |
| 31 ~ 40% | 담당자 승인 → **점장 최종 승인** → ESL 반영 |

**결재선은 목적함수에 넣지 않습니다.** 모델이 결재선을 알면 추천이 왜곡되므로,
모델은 순이익만 보고 결재는 정책이 별도로 판정합니다.
잔여일별 상한(D-2 25% · D-1 35% · D-Day 40%)과 전사 상한 40%는 시스템이 강제합니다.

### 3-1. 반려는 종료가 아니라 제약 추가

점장이 반려하면 대기열에서 사라지는 것이 아니라, **반려 사유가 할인 상한 제약으로 환산되어
같은 목적함수를 다시 풉니다.** 새 추천값은 담당자 재검토 대기열로 돌아옵니다.

| 반려 사유 | 상한 감폭 | 예시 (36% 요청 시) |
| --- | --- | --- |
| 할인율 과다 | −6%p | 30% → 담당자 승인만으로 확정 |
| 재고 여유 | −10%p | 26% |
| 행사 중복 | −12%p | 24% |
| 마진 방어 | −15%p | 21% |
| 기타 | −5%p | 31% → 임계값 초과, **점장 재결재** |

재계산 결과가 30% 이하면 담당자 승인으로 끝나고, 여전히 초과하면 다시 점장 결재로 올라갑니다.
**재추천은 최대 2회**이며, 소진 후에는 ① 점장 수동 가격 지정 ② 할인 미적용(폐기 처리) 중
하나로 반드시 종결됩니다. D-Day 상품은 대기 시간이 곧 회수 가능 물량이므로,
결론이 나지 않는 건을 남기지 않는 것이 운영 원칙입니다.

재추천 화면에는 **반려로 포기한 순이익**이 함께 표시됩니다. 반려에 비용이 따른다는 사실을
숫자로 보여주고, 사유 로그는 이후 정책 상한 튜닝의 근거 데이터가 됩니다.

### 4. 정책과 모델의 분리 — 상한이 추천을 자를 때

잔여일별 상한은 **모델을 바꾸지 않고 결과만 자릅니다.** 상한이 모델 최적점보다 낮으면
대기열에 「상한 적용 · 모델 권장 36%」 배지가 뜨고, 상세 팝업의 손익 곡선에서는
상한 밖 구간이 회색으로 막힌 채 표시됩니다. **정책 때문에 포기한 이익이 눈에 보입니다.**

정책 설정 화면은 슬라이더를 움직일 때마다 그 설정의 영향을 즉시 계산합니다.

| 설정 | 대기열 | 추천 범위 | 점장 결재 | 순이익 개선 |
| --- | --- | --- | --- | --- |
| 권장 (40 / 35 / 25) | 10건 | 16~36% | 3건 | +21.9만원 |
| 예: 20 / 10 / 5 | **5건** | 10~20% | **0건** | +6.3만원 (**−15.7만원**) |

상한을 낮추면 5개 품목이 "그 범위에서는 할인해도 손해"로 판정돼 대기열에서 빠지고,
결재 임계값(30%)이 도달 가능한 최대 할인율(20%)보다 높아져 **2단 결재가 구조적으로
발생하지 않게 됩니다.** 이 경우 설정 화면이 경고 배너를 띄웁니다.

### 5. 마감 가격 경로 — 다이나믹 프라이싱의 시간축

승인은 "지금 몇 %"가 아니라 **마감까지의 인하 스케줄 전체**를 확정합니다.
추천값에서 출발해 마감 시각에 잔여일별 상한에 도달하도록 **1%p씩** 나눕니다.
인하폭이 큰 품목은 시작 시각이 자동으로 앞당겨집니다 (최대 마감 4시간 전).

```
한우 등심 36% → 40%   20:00 ─30분마다 1%p─ 22:00   인하 4회 · ESL 2회
손질 오징어 33% → 40%  20:00 ─17분마다 1%p─ 22:00   인하 7회 · ESL 3회
손질 대파  27% → 40%  18:45 ─15분마다 1%p─ 22:00   인하 13회 · ESL 5회
```

잔여일이 남은 상품(D-1·D-2)은 경로 없이 추천값을 유지합니다.
오늘 다 팔 이유가 없다는 목적함수의 판단과 같은 논리입니다.

> **가격은 1%p 단위로 바뀌지만 ESL 전송은 직전 반영가 대비 3%p 이상일 때만** 합니다.
> 대파 기준 인하 13회 중 전송은 5회. ESL 라벨 배터리 수명을 지키기 위한 가드레일입니다.
> 상세 팝업의 「마감까지 가격 경로」 차트에서 전송 시점(진한 점)을 확인할 수 있습니다.


> `recommended_rate` 는 **0.20 / 0.30 / 0.40 같은 고정값이 아니라 0.01 단위 연속값**입니다.
> DB 컬럼이 정수라면 `numeric(4,3)` 으로 변경해야 합니다.
>
> 승인 시 `approved_rate` · `recommended_rate` · `approval_level`(staff/manager/auto) 을
> **함께** 저장하도록 요청하세요. 담당자가 AI 추천을 얼마나 조정하는지가 학습 데이터가 됩니다.

`POST /api/recommendations/reprice` 요청·응답 형식:

```json
// 요청
{ "store_id": "S01",
  "items": [{ "product_id": "P001", "previous_rate": 0.36,
              "reason_code": "promo_overlap", "memo": "전단행사 중복", "round": 1 }] }

// 응답
[{ "product_id": "P001", "round": 1, "previous_rate": 36, "new_rate": 24,
   "cap": 24, "prob": 71, "expected_gain": 82000, "gain_delta": -32000,
   "needs_manager": false, "ai_note": "행사 중복 반영 · 할인 상한 36% → 24% …" }]
```

> `reason_code` 는 `rate_too_high` · `stock_ok` · `promo_overlap` · `margin_guard` · `etc` 중 하나입니다.
> **반려 사유는 반드시 저장해야 합니다.** 어떤 사유로 몇 번 반려됐는지가 정책 상한을
> 재조정할 때 유일한 근거이기 때문입니다.
